## What it is

A status page is the first thing a customer looks for when something stops working, and the worst
possible time to be paying for one is the moment your own infrastructure is on fire. This one has
no server, no vendor and no account. GitHub Actions runs the checks on a cron, the results are
committed to this repository as plain YAML, and GitHub Pages serves the page. If GitHub is up, the
status page is up.

Everything is in the open. The response times behind every graph are readable files in
`history/`, the uptime percentages are static JSON in `api/`, and incidents are ordinary GitHub
Issues in this repository — opened when a check fails, closed when it recovers. Nothing about the
numbers is ours to massage.

Configuration is one file. [`.upptimerc.yml`](./.upptimerc.yml) lists the endpoints, the custom
domain and the page's branding; the workflows are generated from it.

## Quickstart

There is nothing to install. To add, remove or rename a monitored endpoint, edit the `sites:` list
in `.upptimerc.yml` and push — the workflows regenerate themselves from it.

```bash
gh repo clone ever-just/status && cd status
$EDITOR .upptimerc.yml                 # add a { name, url } under sites:
git commit -am "monitor: add <name>" && git push
gh workflow run "Uptime CI"            # run a check now instead of waiting for the cron
```

## How it works

Seven scheduled workflows do all the work. **Uptime CI** requests each URL every five minutes and
appends the result to that site's file in `history/`. **Response Time CI** and **Graphs CI**
recompute the rolling averages into `api/` and redraw the PNGs in `graphs/`. **Summary CI**
rewrites the status table inside this README between its generated markers. **Static Site CI**
builds the Svelte status page and deploys it to GitHub Pages, and **Update Template CI** pulls
upstream Upptime changes in nightly.

### Repository layout

```text
.
├── .upptimerc.yml        # the only file you edit: sites, CNAME, branding, nav
├── .github/workflows/    # 8 generated workflows (7 on a cron) — do not hand-edit
├── history/              # one YAML file per site: status, code, responseTime
├── api/                  # static JSON endpoints, one folder per site (shields.io reads these)
├── graphs/               # response-time PNGs rendered per site
└── assets/               # page icon
```

Downtime opens an issue labelled `status`; recovery closes it. That issue history is the incident
log the status page renders.

## Known limitations

- **The scheduled checks are paused.** GitHub disables cron workflows in a repository with no
  recent commits, and all seven here are currently `disabled_inactivity` — the last recorded check
  was 2026-06-17. Re-enable with
  `gh workflow enable "Uptime CI"` (repeat for the other six). All six endpoints returned 200 on
  manual check, 2026-09-04.
- **Five-minute resolution.** A blip shorter than the interval is invisible, and GitHub's scheduled
  runners can be several minutes late under load.
- **One vantage point.** Checks run from GitHub's runners only, so this measures reachability from
  there, not from a customer's network.
- **Reachability, not correctness.** A 200 from `/health` does not prove an agent replied to an
  email.
